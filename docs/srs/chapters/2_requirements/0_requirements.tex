\section{Requisitos}
\subsection{Requisitos Funcionais}

\FR{Execução de Pipeline de Ataque}{execucao_pipeline_ataque}{O sistema deve executar ataques através de uma pipeline configurável composta por cinco fases sequenciais: seleção de cenário, seleção de workload dataset, definição de métricas específicas do cenário, seleção de algoritmo/LLM alvo, e definição de attack load.[Must have]}

\FR{Configuração de Fases da Pipeline}{configuracao_fases_pipeline}{O sistema deve permitir ao utilizador selecionar a configuração de cada fase da pipeline através de opções pré-definidas disponibilizadas pelo sistema.[Must have]}

\FR{Configurações Personalizadas}{configuracoes_personalizadas}{O sistema deve permitir ao utilizador inserir configurações personalizadas para cada fase da pipeline, incluindo a adição de novos datasets e attack loads sem modificar o código-fonte da framework. As configurações devem seguir um formato exemplo.[Should Have]}

% \FR{Seleção de LLMs}{selecao_llms}{O sistema deve permitir a seleção de um ou mais modelos de LLMs para serem testados/avaliados.}
\FR{Visualização de Histórico de Resultados}{historico_resultados}{O sistema deve permitir ao utilizador visualizar todos os resultados de ataques que executou anteriormente, apresentando pelo menos para cada ataque: data de execução, configuração da pipeline utilizada, e métricas calculadas.[Must Have]}

\FR{Reutilização de Resultados Públicos}{reutilizacao_resultados}{O sistema deve permitir ao utilizador reutilizar resultados de ataques executados por outros utilizadores e marcados como públicos, apresentando uma confirmação antes da reutilização.[Could Have]}

\FR{Filtragem de Resultados}{filtragem_resultados}{O sistema deve permitir ao utilizador filtrar resultados de ataques utilizando um ou mais dos seguintes critérios: cenário, workload dataset, métrica específica do cenário, algoritmo/LLM, linguagem de programação, e attack load.[Should Have]}

\FR{Comparação de Resultados}{comparar_resultados}{O sistema deve permitir ao utilizador comparar lado a lado os resultados de até 3 ataques diferentes simultaneamente.[Should Have]}

\FR{Registo de Utilizador}{registo_de_utilizador}{O sistema deve permitir a criação de contas de utilizador através de email e password, validando o formato do email e exigindo passwords com no mínimo 8 caracteres.[Must Have]}

\FR{Login de Utilizador}{login_de_utilizador}{O sistema deve permitir ao utilizador autenticar-se através de email e password, gerando uma sessão após autenticação bem-sucedida.[Must Have]}

\FR{Controlo de Visibilidade de Resultados}{controlo_acesso_resultados}{O sistema deve permitir ao utilizador definir, para cada ataque executado, se os resultados são públicos (visíveis por todos os utilizadores) ou privados (visíveis apenas pelo próprio utilizador).[Could Have]}

\FR{Análise de Vulnerabilidades do Código de Linguagens de Programação Comuns}{analise_do_codigo_de_linguagens_de_programação_comuns}{O sistema deve permitir compilar e avaliar através de Static Analysis Tools  as vulnerabilidades do código de linguagens de programação comuns (e.g. python, java, javascript, etc), reportando o tipo e severidade de cada vulnerabilidade encontrada.[Should Have]}

\FR{Suporte de Diferentes Tipos de Dados}{suporte_diferentes_tipos_de_dados}{O sistema deve suportar ataques que utilizem tipos de dados de entrada além de texto, nomeadamente imagens contendo texto e ficheiros de áudio.[Could Have]}

\FR{Suporte a Cenários de Geração de Código}{cenarios_geracao_codigo}{O sistema deve suportar três tipos de cenários de ataque relacionados com código: text-to-code (geração de código a partir de descrição textual), code-to-code (transformação/refatoração de código), e code completion (completamento automático de código).[Could Have]}

\FR{LLM Atacante}{llm_atacante}{O sistema deve implementar metedologias de ataques baseados em LLM de forma a criar prompts adversariais dinamicamente.[Must Have]}

\FR{Armazenamento de Dados}{armazenamento_dados}{O sistema deve armazenar para cada ataque executado: os dados de entrada, as respostas geradas pelos LLMs, as configurações da pipeline utilizada, e os valores calculados de todas as métricas.[Must Have]}

\FR{Cálculo de Attack Success Rate}{calculo_metrica_asr}{O sistema deve calcular a métrica Attack Success Rate (ASR), definida como a proporção de prompts adversariais que contornaram com sucesso os mecanismos de segurança do LLM alvo.[Must Have]}

\FR{Cálculo de Over-Refusal Rate}{calculo_metrica_orr}{O sistema deve permitir calcular o Over-Refusal Rate (ORR), medindo a proporção de prompts benignas que foram incorretamente rejeitadas pelo LLM alvo.[Must Have]}

\FR{Cálculo de Achieved Objective Rate}{calculo_metrica_aor}{O sistema deve permitir calcular o Achieved Objective Rate (AOR), medindo a amplitude do sucesso do ataque através da proporção de objetivos distintos que foram alcançados.[Must Have]}

\FR{Mecanismo de Júri}{mecanismo_juri}{O sistema deve implementar um mecanismo de júri composto por 3  LLMs para classificar cada resposta do modelo alvo como "recusa" ou "cumprimento" do objetivo, utilizando votação por maioria simples para determinar a classificação final.[Must Have]}

\FR{Avaliação da Utilidade}{avaliacao_utilidade}{O sistema deve utilizar o mecanismo de júri de LLMs para classificar cada resposta do modelo alvo quanto à sua utilidade, categorizando-a como "útil", ou "inútil" através de votação por maioria simples.[Should Have]}

\FR{Verificação Anti-Bot}{captcha}{O sistema deve exigir verificação CAPTCHA em cada processo de registo e autenticação de utilizadores para prevenir acesso automatizado por bots.[Could Have]}

\FR{Exportação de Resultados}{exportacao_resultados}{O sistema deve permitir ao utilizador exportar os resultados de ataques em formatos estruturados (JSON, XML), incluindo todas as configurações, prompts, respostas e métricas calculadas.[Could Have]}

\subsection{Requisitos Não Funcionais}

\NFR{Segurança}{O sistema deve implementar autenticação segura com hashing de passwords e e-mails (bcrypt ou superior) para proteger contas de utilizadores.}


\NFR{Usabilidade}{O sistema deve permitir que utilizadores configurem e iniciem um ataque básico em menos de 5 minutos, utilizando configurações pré-definidas.}

\NFR{Compatibilidade}{O sistema deve funcionar nos principais navegadores web (Chrome, Firefox, Safari) nas suas versões mais recentes.}

\NFR{Conformidade}{O sistema deve permitir aos utilizadores exportar e eliminar os seus dados pessoais, cumprindo requisitos básicos do GDPR.}
